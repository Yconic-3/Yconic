# 0005. 데이터베이스와 백엔드 API 구성

- 날짜: 2026-11-11
- 상태: 채택 (작업기·파일 저장은 임시)
- 결정자: Yconic

## 배경

지금까지 사용자 화면과 관리자 화면은 브라우저 저장소의 모의 백엔드(`apps/web/src/mock`)로 돌아갔다.
데이터가 브라우저마다 따로 있고, 로그인도 서버 검증이 없었다.
두 화면을 기준으로 실제 데이터베이스와 API를 만든다. 순서는 데이터베이스 설치 → 테이블 설계 → 테이블 반영 → API 개발 → 프론트엔드 적용이다.

## 결정

1. **데이터베이스는 PostgreSQL 18** (설계 문서 9장).
   - 개발용은 Docker 없이 `pnpm db:start`로 프로젝트 안에서 켠다 (npm `embedded-postgres` 실행 파일, 포트 5433).
     Windows에서 경로에 한글이 있으면 PostgreSQL이 시작하지 못해서 실행 파일을 `~/.yconic`으로 한 번 복사해 쓴다.
   - 서버·CI에서는 공식 `postgres:18` 이미지를 쓴다 (`infrastructure/docker-compose.yml`, `.github/workflows/ci.yml`).
2. **테이블과 마이그레이션은 Drizzle ORM** (`packages/database`). 7개 테이블, 설명은 `docs/database.md`.
   열거형 값은 `packages/shared-types`의 목록에서 만들어 화면·서버·DB가 같은 값을 쓴다.
3. **API는 NestJS** (`apps/api`, 포트 4000, 설계 문서 2·9장).
   - 주소와 요청·응답 모양은 `packages/shared-types`의 `admin-api.ts`, `user-api.ts`, `auth.ts` 주석 그대로다.
   - 권한표·상태 전이·자기 승인 금지는 화면과 같은 shared-types 함수로 서버에서 다시 검사한다.
   - 로그인은 이메일·비밀번호 → 무작위 토큰. 비밀번호는 scrypt 해시, 토큰은 SHA-256 해시로만 DB에 둔다 (30일).
4. **웹앱은 `NEXT_PUBLIC_API_MODE`로 데이터 소스를 고른다.** 기본은 `http`(API), 서버 없이 화면만 볼 때 `mock`.
5. **임시로 정한 것** (설계 문서와 다름, 나중에 바꾼다)
   - 제작 작업기(content-worker)는 별도 앱과 Redis + BullMQ 대신 **API 서버 안의 모듈**(`apps/api/src/worker`)이
     DB를 1초마다 확인해 처리한다. 분석기와 음성 생성은 아직 모의(`@yconic/content-analysis`)다.
     여러 서버가 떠도 한 작업은 한 곳에서만 처리하도록 행 잠금(`FOR UPDATE SKIP LOCKED`)을 쓴다.
   - 올린 영상은 S3 호환 저장소 대신 **API 서버 폴더**(`apps/api/storage`)에 두고 `/media/...`로 내보낸다.
     주소를 아는 사람은 누구나 받을 수 있으므로 실제 서비스 전에 서명된 주소로 바꿔야 한다.

## 결과

- 두 화면이 같은 DB를 보므로 관리자가 공개한 운동이 모든 사용자에게 바로 나온다.
- 관리자 API는 서버에서 로그인·권한을 검사한다. 화면에서만 막던 것을 서버가 다시 막는다.
- 개발자는 `pnpm db:start`, `pnpm db:setup`, `pnpm dev:api`, `pnpm dev:web` 네 단계로 전체를 띄운다.
- API 테스트는 쓰고 버리는 PostgreSQL을 직접 켜서 실제 HTTP로 확인한다 (CI에서는 서비스 컨테이너).
- 다음 단계: 실제 분석기·TTS 연결, 작업기를 `apps/content-worker` + BullMQ로 분리, 파일을 S3 호환 저장소로 옮기기,
  로그인 시도 횟수 제한, 로그인 화면의 체험용 계정 목록을 개발 환경에서만 보이기.
