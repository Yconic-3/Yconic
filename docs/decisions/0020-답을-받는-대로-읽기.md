# 0020. 답을 받는 대로 읽기

- 날짜: 2026-11-28
- 상태: 채택
- 결정자: Yconic

## 배경

조작 명령은 빨라졌지만(결정 0019), 질문에 대한 답은 그대로 4초쯤 걸렸다. 정보를 찾아 답할 때는 AI를 두 번 부르고, 답이 다 만들어진 뒤에야 읽기 시작했기 때문이다.
답이 두세 문장이면 마지막 글자가 나올 때까지 1~2초를 조용히 기다렸다.

## 결정

1. **에이전트가 답을 글자가 나오는 대로 보낸다** (`POST /chat/stream`).
   - 응답은 한 줄에 JSON 하나씩이다: 글자(`text`), 버리기(`reset`), 할 일(`actions`), 끝(`done`), 실패(`error`). 모양은 `shared-types`의 `AgentStreamEvent`.
   - 끝(`done`)에 담긴 답이 기준이다. `POST /chat`의 응답과 같다. `POST /chat`은 그대로 둔다.
   - 사이의 프록시가 모아 두었다가 한꺼번에 보내지 않도록 `Cache-Control: no-transform`과 `X-Accel-Buffering: no`를 붙인다. Vercel → 업체 nginx → 서버의 웹앱 → 에이전트를 모두 거쳐도 글자가 나뉘어 도착하는 것을 확인했다.
   - Claude는 `ai-common`의 `RunOptions.onText`로 스트리밍한다.
2. **화면은 읽을 만큼 모인 곳부터 읽는다** (`apps/web/src/user/lib/stream-speech.ts`).
   - 문장이 끝난 곳(. ! ? 뒤에 띄어쓰기)에서 끊어 읽는다.
   - **맨 처음 조각만은 쉼표에서도 끊는다.** 첫 문장이 길면 문장이 끝나기를 기다리는 동안 조용하기 때문이다. 쉼표 앞의 말이 10자보다 짧으면 끊지 않는다.
   - 그 뒤로는 문장 단위로만 끊는다. 자주 끊으면 말이 뚝뚝 끊겨 들린다.
   - 조각은 차례로 읽는다. 사람이 말을 끊으면 뒤의 조각은 읽지 않는다.
3. **할 일이 있는 답은 먼저 읽지 않는다.**
   - 화면을 바꾸거나 재생을 조작하는 답은 끝까지 받은 뒤 예전 순서대로 한다 (할 일 → 답 읽기 → 묻기). 읽는 중에 화면이 바뀌지 않게 하기 위해서다.
   - 그래서 먼저 읽는 것은 설명·주의사항·추천처럼 말로만 답하는 경우다. 긴 답은 대부분 이 경우다.
   - 글로 물었거나 음성 안내를 껐으면 하지 않는다.
4. **맞장구(0019)와 함께 쓴다.**
   - 글자가 오기 시작하면 아직 하지 않은 맞장구는 하지 않는다.
   - 맞장구를 읽는 중이면 다 읽은 뒤에 답을 읽기 시작한다.
5. **에이전트가 스트림을 모르면 예전 방식으로 받는다.**
   - 웹앱 안 에이전트(`AGENT_IN_WEB=1`, 서버 없이 Vercel만 쓸 때)는 `/chat/stream`이 없다. 화면이 404를 받으면 `/chat`으로 받는다.

## 결과

- 좋은 점: 말로만 답하는 긴 답을 1초쯤 일찍 읽기 시작한다. 답이 길수록 더 일찍 시작한다.
- 한계
  - 답 전체가 끝나는 시각은 같다. 줄어드는 것은 읽기 시작할 때까지의 시간이다.
  - 한 문장짜리 짧은 답은 달라지지 않는다.
  - 첫 조각을 쉼표에서 끊어 읽으면, 기기의 목소리에 따라 그 자리에서 말이 끝난 것처럼 들릴 수 있다. 어색하면 `FIRST_CHUNK_AT_COMMA`를 `false`로 바꾼다 (그러면 늘 문장 단위로 읽는다).
  - 읽기 시작한 뒤에 연결이 끊기면 읽은 데서 멈춘다.
  - 웹앱 안 에이전트에서는 받는 대로 읽지 않는다.
- 나중에: 정보를 찾는 호출을 줄이기(공개 운동이 적을 때는 목록이 이미 대화에 있다), 더 빠른 모델 시험, 미리 만든 음성 파일.
